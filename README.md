## 打分不靠 AI 拍脑袋

早期版本是直接问 AI「这条值几分」。问题很明显：同一篇文章今天问是 0.8、明天问是 0.6，两条机会之间也没法比——**这不是打分，是感觉**。

现在改成 **「AI 只做观察，公式做判断」**：

1. AI 不许给总分，只回答一组**能从原文看出来的事实型小问题**，每个 1–5 分，每一档都有明确定义。
   比如「单笔收费」：5 = 一单 ≥1 万元，3 = 300–2000 元，1 = 低于 50 元。
2. 这些分数怎么加权、什么情况下一票压制，**全部写死在 `scoring.py` 的公式里**。

打分框架不是自己编的，来自两套公开成熟的方法，按"完全不会写代码的人"重新配了权重：

- Josh Kaufman《The Personal MBA》**十项经济性评估**（紧迫度 / 市场规模 / 定价潜力 / 交付成本 / 独特性 / 上市速度 / 前期投入 / 追加销售 / 长青度）
- 独立创业圈的 **BB Score**（10 因子加权 0–100）

最后你在卡片上看到**一个最该看的数**——「适合你启动指数」。商业化潜力、可行性两个分数仍由公式算出、在后台参与排序与「该不该推」的判断，但不再堆在卡片上，让每张卡一眼能扫完：

| 指标 | 含义 |
|------|------|
| 🎯 **适合你启动指数** 1–10 | 综合排序，一眼看出今天最该动手哪条（9–10=今天最该抄 / 7–8=值得动手 / 5–6=可以看看 / <5=参考为主） |

还有几条**一票压制**规则，防止总分虚高掩盖致命短板：

- 需要写代码 → 最高 3 分
- 疑似卖课 / 卖铲子 → 最高 3 分
- 没写清客户从哪来 → 最高 6 分
- AI 没按格式给全打分依据 → 最高 4 分（宁可漏推，不可虚高）

> 校准过一次：全部打中位数（每项 3 分）得 5 分，不是 6 分。平庸的机会就该看起来平庸。

**连推给你的操盘手本人也要过这一关**：每个案例在推送前会做一次「商业底层逻辑体检」，结构性有问题的（纯卖铲子、没有真实产品、只有流量没有收入证据）直接不推，轻度存疑的会在卡片上标出警告。

## 你点的「想做 / 没兴趣」，它收得到

每条机会下面有两个按钮：👍 这条我想做 / 👎 没兴趣。

**先说清楚原理**：飞书群机器人的 webhook 是**单向**的——只能往群里发，收不到你点了什么。想真正接收按钮回调，得注册飞书应用 + 提供一个公网回调地址 + 常驻服务器，对这个"零服务器"的项目来说太重了。

所以换了个不用服务器的办法：

1. 点按钮 → 打开一个**已经填好内容**的 GitHub Issue 页面（标题、标签、机会编号都预填好了）；
2. 你再点一下"提交"，就完成反馈；
3. 第二天运行时，系统通过 GitHub API 把这些 Issue 读回来，调整排序。

调整幅度**刻意做得很小**（±1~2 分）：点过"想做"的方向以后会往前排，点过"没兴趣"的往后压。不会因为你点了一两次，明天推送就完全变样。

## English summary

**OPC DigDaily** is a **free daily intelligence report for aspiring one-person business owners who cannot code.**

Every day it automatically finds, analyses and delivers:

- **1–2 teardowns** of real solopreneurs — what they sell, where their customers come from, how they get paid;

## 🅱️ 路线 B：自己部署（技术向，可选）

如果你有自己的 AI Key 和飞书机器人，也可以把这套系统 fork 过去自己跑。步骤：

```bash
git clone https://github.com/wsjxphz-png/opc-digdaily.git
cd opc-digdaily
python -m venv .venv && .venv/Scripts/activate   # Windows；mac/Linux 用 source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env                              # 填入 FEISHU_WEBHOOK_URL 与 AI_API_KEY

python main.py --dry-run                          # 先演练：跑完整流程，但不推群、不写历史
python main.py --once                             # 确认没问题再真跑（会真实推送到飞书群）
```

`--dry-run` 会把渲染好的卡片存到 `storage/dry_run/*.json` 供你检查，**不发消息、不写任何状态文件**。改完配置先跑这个，别拿群当测试环境。

也可推到 GitHub 后用 Actions 定时运行（见 `.github/workflows/daily-push.yml`，默认北京时间每天 20:00）。**所有密钥走环境变量 / Secrets，绝不写进代码。**

需要配的 Secrets：

| Secret | 必填 | 说明 |
|--------|------|------|
| `FEISHU_WEBHOOK_URL` | ✅ | 飞书群机器人地址 |
| `AI_API_KEY` | ✅ | AI 模型密钥 |
| `TWITTER_COOKIES` | ⬜ | 抓 X 用，不填自动跳过 |
| `GITHUB_TOKEN` | ⬜ | Actions 自带，无需手动创建 |

> ⚠️ **别删 workflow 里的 `Persist state` 那一步。** GitHub Actions 每次都是全新容器，`storage/` 不写回仓库的话，机会库永远停在"第 1 次出现"、操盘手轮转会反复拆同一批人、去重历史每天清零。

> 💡 **说实话**：路线 A 更省心。你自己搭要准备 AI Key（花钱）、配 webhook、调试环境；直接进群，这些都替你做好了，而且每天的内容一样不少。除非你有定制需求（比如想加自己的信息源、推到别的平台），否则没必要重复造轮子。
